# FleetOps Demo Agent Rules

## Repository Role

- Этот репозиторий — **автономный демонстрационный стенд** FleetOps (далее «демо»): статическое Vue 3 SPA без backend, без API-коннекторов, с детерминированным генератором демо-данных.
- Назначение: воспроизведение пользовательских сцениев и управленческих срезов из технических заданий (ТЗ) для показа заказчикам. Демо не является продуктовым кодом FleetOps и не заменяет `fleetops-frontend`.
- Источник требований: `ZIMA_FleetOps-ТЗ_v2.0_на_доработку_демо-стенда.md` (актуальная итерация) и план переработки `TZ_V2.0_REWORK_PLAN.md`; приёмочный маршрут — `ZIMA_FleetOps-общий_сценарий_демонстрации_и_приёмки_демо-стенда_v1.1.md`; акт приёмки и реестр ACC-001…ACC-035 — `ZIMA_FleetOps-отчёт_приёмки_демо-стенда_по_ТЗ_v2.0.md`; план устранения замечаний — `TZ_V2.0_ACCEPTANCE_FIX_PLAN.md`. Предыдущие ТЗ (v1.4/v1.5/v1.6) и `TZ_V1.6_PLAN.md` — реализованная база и исторический контекст.
- Коммитить изменения демо из этого репозитория; ветка `master`, remote `origin`.

## Контрольный контракт данных (Отчёт приёмки §5; пересобран под ACC-024)

- 33 инцидента = 32 подтверждённых классифицированных закрытых + 1 активный неклассифицированный INC-2026-0033 (живой сбрасываемый) с нулевым подтверждённым влиянием до прохождения сценария.
- Столкновения: 5 подтверждённых случаев (5 ч 10 мин / 265 417 ₽). Сумма потерь 986 667 ₽ (отклонение −2 ₽ от ТЗ задокументировано) — инцидентный контракт сохранён при масштабировании парка.
- Масштаб (ACC-024, Отчёт §10.2/§12): **72 робота** — РЦ Подольск 30 (флагман), РЦ Обухово 24, ФФЦ Домодедово 18. Модели: Ronavi H1500, HIK Robot AMR, Geek+ P-series + M-series.
- Миссии роботов (RMS/FMS): `MISSION_STATS` в generator.ts — демо-допущение; WMS-интеграция не подключена, миссии не выдаются за план склада (Отчёт §10.3).

## Доменные правила (фиксы приёмки)

- Все мутации стора проходят permission-гарды (`guard()` в `useDemoData.ts`); финансовая и директорская роли строго читающие. Право возврата робота — `incidents.recover`, завершения ТОиР — `maintenance.complete`/`maintenance.return`.
- Возврат робота в парк гейтован `returnGate()`: финальная причина + подтверждённое восстановление + завершённый сервис с положительным контрольным запуском.
- Живой сценарий детерминирован: действия пишут сценарные метки `SCENARIO_STEPS_MIN` (09:12 → 09:37 → 17:40), а не wall-clock. Контрольные 25 мин / 29 167 ₽ и 8 ч 28 мин.
- Безопасность — авто-запись при назначении координатора; отдельной кнопки нет (ACC-029).
- Метрики — только через `src/data/metrics.ts` (240 робот-ч на робота, 17 280 на парк из 72). Экранные формулы доступности запрещены. Паспорта метрик — `src/data/metric-passports.ts` (ACC-033/034); новая метрика на дашборде без паспорта запрещена.
- Ролевые главные: SITE_MANAGER → «Мой объект»; FLEET_OPERATIONS_MANAGER/SERVICE_MANAGER → «Портфель»; OPERATIONS_DIRECTOR/FINANCE_MANAGER → «Экономика»; SERVICE_ENGINEER → «Сервис и ТОиР» (мои работы).
- Псевдо-живые числа (`Math.random`, статические «Обновлено HH:MM») запрещены.

## Tooling

- Менеджер пакетов — **npm**. pnpm не использовать: ни для установки зависимостей, ни для запуска скриптов, ни для работы с lockfile. Команды: `npm install`, `npm run dev`, `npm run build`, `npm test`, `npm run lint`.
- `npx` допустим только для инструментов без npm-скрипта (например `npx playwright test`).

## Demo Architecture

- **Стек**: Vue 3 + TypeScript + Vite, shadcn-vue (reka-ui), Tailwind v4, Chart.js, pinia, vue-router.
- **Данные**: `src/data/generator.ts` — единственный источник демо-данных (33 инцидента, 72 робота, 3 объекта, 9 зон, 10 состояний парка, замещения, 2 типа интервалов, 23 работы ТОиР, миссии RMS/FMS). Никаких API-вызовов; всё вычисляется локально при старте и хранится в pinia-сторе (`useDemoData`).
- **Русские подписи**: `src/data/labels.ts` — единственное место перевода машинных кодов (статусы, причины, типы) на русский. Машинный код допустим только как вторичный текст.
- **Роли**: `src/data/roles.ts` — 8 демонстрационных ролей с permission-наборами; логин — выбор карточки роли (без реальной аутентификации). Объектовая модель доступа: SITE_MANAGER видит только свой объект (редирект на «Мой объект»).
- **Страницы**: `src/pages/*` — Мой объект, Обзор, События, Инциденты, Карточка инцидента, Простои, Аналитика, Роботы, Объекты, Зона, ТОиР, Отчёты.

## Data Invariants (обязательные инварианты генератора, ТЗ v2.0 §10.4)

Требования проверяются юнит-валидатором (`npm test`) и должны выполняться всегда:

- Масштаб (ACC-024): ровно 72 робота (30/24/18 по объектам), 3 объекта, 9 зон; робот принадлежит одному объекту и не более чем одной текущей зоне; одна единица — одно текущее состояние (10 состояний парка §5.2); стартовые состояния: 49 работают / 7 резерв / 8 зарядка / 7 сервис / 1 авария.
- Ровно 33 канонических номера INC-2026-XXXX; стартовые срезы: 5 активных инцидентов, 9 роботов в бэклоге, 6 требуют разбора.
- Два типа интервала: «Операционное влияние» (потери процесса) и «Техническая недоступность» (доступность актива, без потерь). Потери = подтверждённые минуты влияния × ставка объекта, округление до рубля на интервал. Один интервал не учитывается дважды; неподтверждённые — не в потерях.
- Контрольные суммы: влияние 1075 мин / 986 667 ₽ (ТЗ 986 669 — недостижимо в целых минутах, отклонение −2 ₽ задокументировано); технедоступность 49 ч 30 мин; плановые часы 17 280 (72 × 8 ч × 30 дней); техдоступность 99,71 %; операционная доступность мощности 99,90 %. Разрезы по причинам и объектам сходятся к одним итогам.
- Две контрольные точки: «Процесс восстановлен» (ввод резерва — прекращает потери) и «Робот возвращён в парк» (закрывает недоступность). Между ними — состояние «Процесс восстановлен, сервис продолжается». Закрытие инцидента требует: безопасность, финальную причину, восстановление, обе контрольные точки, решение по простою.
- Эталонный кейс INC-2026-0001 (25 мин / 29 167 ₽ / 8 ч 28 мин, FMR-001←FMR-012) + живой сбрасываемый INC-2026-0033 (открытые интервалы вне контрольных сумм). Сброс восстанавливает набор и повторно проходит валидатор.
- Источники: WMS передаёт только процессные события; технические сигналы — от RMS/FMS/RCS или контроллера; ручное подтверждение — отдельный тип доказательства.
- Хронология неубывающая; длительности вычисляются из меток; автоматические записи истории помечены «авто».
- CA-014 «Ошибка конфигурации» запрещена как универсальная причина.
- Данные и формулы заморожены после DMO-01; изменения набора — только через явное решение с пересогласованием контрольных сумм.

## Design System

- [DESIGN.md](DESIGN.md) — обязательный design spec демо (общий с продуктовой темой: glassmorphism dark-first, 4 палитры, 3 уровня токенов в `src/assets/styles/style.css`).
- Новые компоненты используют только design-токены; hardcoded HEX запрещён. Статусные цвета — только через `--status-*`. Числовые плитки — `tabular-nums`.
- Glassmorphism (`backdrop-filter`) только для карточек верхнего уровня, хедера, модалок и сайдбара — не для ячеек таблиц и рядов списков.
- Presentation rule: ролевые главные сначала показывают существующее управленческое решение и его drill-down, затем KPI и доказательные данные. Для этого использовать общие `page-hero` и Card tones; таблицы, строки и form controls остаются матовыми. Palette-aware компоненты, включая Chart.js, читают только semantic CSS tokens.

## UI Source of Truth

- Интерактивные элементы строятся только на shadcn-vue (`src/components/ui/*`); нативные `<button>/<input>/<select>/<table>` для пользовательского UI запрещены. Инвентарь: [SHADCN_COMPONENTS.md](SHADCN_COMPONENTS.md).
- Русский язык — основной текст интерфейса; англоязычные машинные статусы (HIGH, CLOSED, CONFIRMED, OPERATIONS, IT …) пользователю не показываются — только через `labels.ts`.

## Execution

- Перед коммитом: `npm run lint`, `npm run format:check`, `npm run type-check` — все чистые; `npm run build` собирается без ошибок.
- Данные: любое изменение `generator.ts`, влияющее на набор, сопровождается прогоном валидатора (`npm test`) — ноль ошибок по хронологии, обязательным полям, источникам, идентификаторам, длительностям и экономике.
- E2E: `npx playwright test` — dev-сервер :5180 поднимается автоматически (webServer, reuseExistingServer); outputDir в `%TEMP%` — артефакты внутри проекта роняют vite-watcher (EBUSY) и вызывают page-reload посреди тестов.
- Изменение UI проверяется вручную в браузере (`npm run dev`, порт 5180): маршрут, сценарий, наблюдаемый результат фиксируются в коммите/плане.
- Коммит-месседжи: `demo: <суть>` или со ссылкой на пакет плана, например `demo: A2 — redistribute CA-014`.
- Не коммитить: node_modules, dist, локальные артефакты, скриншоты вне `docs/screenshots`.

## Verification Levels (многоуровневая проверка)

Проверка демо многоуровневая. Уровни (сверху вниз):

```
┌───────────────────────────────────────────────────────────────┐
│  Сквозной прогон (E2E)                                        │
│  ловит: стыки, конфигурацию, реальные данные, регрессии UX    │
│  не ловит: редкие ветки логики, граничные значения            │
├───────────────────────────────────────────────────────────────┤
│  Контрактные и интеграционные проверки                        │
│  ловят: расхождение схем, обратную совместимость API          │
│  не ловит: то, что происходит после интеграции слоёв          │
├───────────────────────────────────────────────────────────────┤
│  Юнит-тесты                                                   │
│  ловят: логику функции в изоляции                             │
│  не ловит: всё, что находится между функциями                 │
├───────────────────────────────────────────────────────────────┤
│  Исполняемые архитектурные правила (arch-check)               │
│  ловят: структурные нарушения до появления дефекта            │
│  не ловит: поведение                                          │
├───────────────────────────────────────────────────────────────┤
│  Линтер и типы                                                │
│  ловят: форму                                                │
│  не ловит: смысл                                              │
└───────────────────────────────────────────────────────────────┘
```

- **Право ставить passing принадлежит только верхнему уровню.** Работа считается прошедшей проверку только по результату сквозного E2E-прогона; чистые линтер/типы/юнит-тесты сами по себе права объявлять passing не дают.
- Каждый уровень обязателен сам по себе: падение любого уровня — блокер, независимо от верхних уровней.
- Для демо-стенда актуальные уровни: линтер/типы (`npm run lint`, `npm run type-check`), юнит-валидатор данных (`npm test`), E2E (`npx playwright test`) + ручная браузерная проверка сценария приёмки. Контрактный уровень и arch-check включаются по мере появления соответствующих поверхностей.

## Рубрика оценки (каждое измерение — A/B/C/D, ниже B = отклонить)

| Измерение                | A                            | B                       | C                | D                     |
| ------------------------ | ---------------------------- | ----------------------- | ---------------- | --------------------- |
| Корректность             | все тесты + граничные случаи | основной поток проходит | частично         | сборка падает         |
| Соответствие архитектуре | полное                       | мелкие отклонения       | явные отклонения | грубые нарушения      |
| Покрытие тестами         | основной поток + границы     | только основной поток   | только каркас    | нет тестов            |
| Обработка ошибок         | все внешние сбои обработаны  | основные обработаны     | частично         | ошибки проглатываются |
| Наблюдаемость            | логи на критических путях    | базовые логи            | почти нет        | нет                   |

Правила:

- каждая оценка обязана содержать ссылку на доказательство (файл:строка, вывод теста, лог);
- «мне кажется» и «выглядит нормально» — не доказательство, оценка без ссылки недействительна;
- один D или два C = отклонить с конкретным списком того, что исправить.
